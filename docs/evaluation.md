# Design-system evaluation — August 2026

An audit of `@rtkelly13/design-system` as a *system* rather than a component
library: how well the token layer holds, how much of the surface is specified,
and what the hosting change in this branch does and does not fix.

The companion audit in the blog repo
([`docs/design-system-evaluation.md`](https://github.com/rtkelly13/blog/blob/main/docs/design-system-evaluation.md))
covers the blog's Storybook. This one covers the package.

## Verdict

Architecturally this is stronger than most in-house design systems. The
semantic token layer is genuinely well-designed, and the reasoning is written
down where it will be read. The weaknesses are all **adoption and coverage**
gaps, not design gaps: the good abstraction is about half-used, and the test
layer that is described as a gate covers a sixth of the surface.

## Strengths

**The semantic layer is the right abstraction.** `src/lib/theme.ts` splits
colour into `Emphasis` (visual hierarchy) and `Intent` (communicated meaning) —
a distinction most systems miss, and the one that decides whether a retheme is
mechanical or a redesign. `accentVar()` degrades to the primary accent on an
unknown token rather than emitting `color: undefined`, which is the correct
failure mode for a prop that a consumer can typo.

**The one genuinely subtle CSS decision is both correct and explained.**
`theme.css` re-declares the `--ds-*` block on the mode classes as well as
`:root`, because `var()` substitutes where a property is *declared*, not where
it is used — without it, a `.sketch` panel nested in a dark page would inherit
the root theme's resolved literals. That is the kind of thing that is usually
discovered twice; here it is documented in place.

**Deprecation is handled properly.** `LegacyAccent` maps the old palette names
onto the same variables their semantic counterparts use, so migrating a call
site is a rename with a guaranteed-empty visual diff.

**The testing philosophy is unusually clear-headed.** `tests/story-ready.ts`
asserts Storybook actually mounted before any screenshot, because Storybook
always paints *something* — AGENTS.md records that every baseline in the repo
was once a screenshot of the "No Preview" panel and the suite passed throughout.
Splitting visual regression (a gate) from the walkthrough (a review aid, not a
gate) is the right call, and the cross-theme walkthrough catches the failure a
single-theme pixel baseline structurally cannot.

## Gaps

### 1. The semantic layer is about half-adopted

AGENTS.md is unambiguous: components "must **never** reference
`--brutalist-cyan`, `--color-white`, `--border-color` or the `brutalist-*`
Tailwind utilities directly."

Measured across `src/components/`:

| | Count |
| --- | --- |
| Palette utilities (`bg/text/border-brutalist-*`, `text-white`, `bg-black`, `border-white`) | **83 occurrences in 9 files** |
| Semantic utilities (`bg/text/border-{accent,intent,surface,content,edge}-*`) | 62 occurrences |

`Button.tsx` — the most-copied component in any system, and therefore the one
that teaches the pattern — is entirely palette-based:

```tsx
cyan: 'bg-brutalist-cyan text-black border-white shadow-hard-md …'
```

This is not currently a *bug*: `.dim` and `.sketch` remap the raw palette too,
so these components still retheme. The cost is that the abstraction cannot be
relied on. Any future mode that changes role assignment rather than just hue —
say a high-contrast mode where "primary" must stop being cyan — breaks exactly
these nine files, and the rule that would have prevented it is documented but
not enforced.

Worth fixing in this order: `Button`, `Badge`, `Card` (most-copied), then the
rest. A lint rule banning `brutalist-*` utilities in `src/components/` would
make the documented rule real; today nothing checks it.

### 2. Visual regression covers 5 stories

`tests/visual.spec.ts` contains 5 cases (`button component`, `button
bracketed`, `card`, `slide deck`, `lorem ipsum blog post`) against 37
components and ~30 stories. It is listed in AGENTS.md as a required check
alongside typecheck and build, which reads as far broader coverage than it has.

AGENTS.md already explains the reason it stays small — a new story needs a
baseline generated by dispatching the snapshot workflow before a case can be
added — so this is friction, not neglect. But `DocsPortal`, `SaasLandingPage`,
`AdminDashboardLayout` and `DataTable` are the largest compositions in the repo
and none is snapshotted.

### 3. 12 components have no story at all

`AsciiDivider`, `BlogPost`, `BracketText`, `DataTable`, `DocsLinkProvider`,
`ExperimentsView`, `Modal`, `PageHeader`, `PageTitle`, `Pagination`,
`SectionContainer`, `mdxComponents`.

`Modal` and `DataTable` matter most: both have interactive states that are
invisible in a static catalogue, and `Modal` is the component most likely to
have theme-specific overlay problems.

### 4. No accessibility checking in the package's own Storybook

`.storybook/main.ts` loads only `@storybook/addon-docs`. The **blog's**
Storybook runs `@storybook/addon-a11y`. That is backwards: contrast and focus
failures introduced here propagate to every consumer, and a brutalist palette
on black — cyan `#22d3ee`, yellow `#facc15`, pink `#ec4899` — is precisely the
kind of high-saturation scheme that passes by eye and fails on measurement.
`sketch` inverts the whole relationship and is untested.

Adding `@storybook/addon-a11y` here is a one-line change with a high yield.

### 5. Fonts are fetched from Google at runtime

`src/styles.css` opens with an `@import` of `fonts.googleapis.com`, and
`.storybook/preview-head.html` repeats it. The blog, by contrast, self-hosts
the same four families via `@fontsource/*`.

Three costs: a render-blocking third-party request on every consumer's first
paint; a privacy consideration the blog has already decided against; and a hard
dependency on network reachability — this was the sole reason the Storybook
built in this branch rendered an error panel in a sandboxed environment, and it
would behave the same on any restricted network. Switching to `@fontsource`
would align the package with its own primary consumer.

### 6. Two version-drift problems

- **The blog cannot receive updates.** It depends on `"@rtkelly13/design-system": "^0.0.5"`.
  Under semver, a caret range on `0.0.x` matches *only* `0.0.5` — so the blog is
  pinned behind the published `0.1.2` and will never resolve forward. This is
  almost certainly unintentional, and remains the cheapest high-value fix. It
  needs a change in the blog repo, not here.
- ~~**Storybook is two majors behind.**~~ **Resolved by #23**, which took this
  repo from `8.6` to `10.5` and dropped `@storybook/addon-essentials` — it has no
  v10 release, its features having moved into core. Host and ref are now on the
  same major, so composition no longer depends on cross-major tolerance.

## What this branch changes

Hosting only. `design-system.ryankelly.dev` serves this Storybook from `main`;
`preview.design-system.ryankelly.dev` serves the `preview` branch; the blog's
Storybook is composed into the sidebar so one URL shows both tiers.

None of the gaps above are addressed by it. Gaps 4 and 6 are the cheapest to
close and would be reasonable follow-ups; gap 1 is the one that decides whether
the semantic layer is load-bearing or decorative.
